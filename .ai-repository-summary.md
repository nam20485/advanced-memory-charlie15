# Repository Summary: advanced-memory-charlie15

## Overview

This repository implements an MCP (Model Context Protocol) server-based advanced memory, recall, verification, and reasoning system that combines **GraphRAG** for structured knowledge retrieval and **Mem0** for stateful agentic memory management. The system creates a "digital expert" AI agent with both deep domain knowledge and personalized, evolving memory capabilities.

**Project Type**: Distributed AI System (Microservices Architecture)
**Primary Language**: C# (.NET 9.0)
**Secondary Languages**: Python 3.11 (for AI/ML services)
**Repository Size**: Medium (multi-project solution)
**Target Runtimes**: .NET 9.0, Python 3.11, Docker containers

## Architecture

### High-Level Components

1. **MCP Server** (ASP.NET Core) - Main API server implementing Model Context Protocol
2. **Provider Libraries** - Knowledge, Memory, Grounding, and Orchestration providers
3. **Blazor UI** - WebAssembly-based monitoring dashboard
4. **Python Services** - GraphRAG and Mem0 gRPC/REST microservices
5. **Infrastructure** - Neo4j graph database, Qdrant vector database
6. **.NET Aspire AppHost** - Service orchestration and development dashboard

### Key Technologies

- **Frameworks**: ASP.NET Core Web API, Blazor WebAssembly, .NET Aspire
- **AI/ML**: Microsoft GraphRAG, Mem0, OpenAI/Azure OpenAI
- **Databases**: Neo4j (knowledge/memory graphs), Qdrant (vector embeddings)
- **Testing**: xUnit, Moq, FluentAssertions, Testcontainers
- **Containerization**: Docker, Docker Compose
- **CI/CD**: GitHub Actions

## Build and Validation

### Prerequisites

- .NET 9.0 SDK (version 9.0.0 or later with rollForward: latestFeature)
- Docker Desktop (for infrastructure services)
- Python 3.11+ (for GraphRAG/Mem0 services)
- OpenAI API key or Azure OpenAI endpoint
- PowerShell 7+ (for scripts)

### Build Commands

**ALWAYS run these commands from the repository root directory.**

1. **Restore dependencies** (ALWAYS run first):
   ```bash
   dotnet restore
   ```
   Expected duration: 15-30 seconds
   Preconditions: global.json must exist, internet connection required
   Postconditions: All NuGet packages restored to .nuget cache

2. **Build solution** (run after restore):
   ```bash
   dotnet build --configuration Release
   ```
   Expected duration: 30-60 seconds
   Preconditions: Dependencies restored, .NET 9.0 SDK installed
   Postconditions: All projects compiled to bin/Release/net9.0 (or net8.0 for AppHost)

3. **Run tests**:
   ```bash
   dotnet test --configuration Release --verbosity normal
   ```
   Expected duration: 10-30 seconds (will increase as tests are added)
   Preconditions: Solution built successfully
   Postconditions: Test results displayed, exit code 0 if all pass

4. **Format check** (ALWAYS run before committing):
   ```bash
   dotnet format --verify-no-changes
   ```
   Expected duration: 5-10 seconds
   If this fails, run `dotnet format` to auto-fix formatting issues

5. **Run application via Aspire**:
   ```bash
   dotnet run --project src/AdvancedMemory.AppHost
   ```
   Expected duration: 10-20 seconds to start
   Access Aspire dashboard at: https://localhost:15888
   Preconditions: Docker Desktop running (for Neo4j, Qdrant containers)

### Infrastructure Services

**CRITICAL**: Before running the application, start infrastructure services:

```bash
docker-compose up -d neo4j qdrant
```

Verify services are healthy:
```bash
docker-compose ps
```

Expected output: neo4j and qdrant containers in "Up (healthy)" state

**Timing Note**: Neo4j takes 20-30 seconds to fully initialize. If the application fails to connect, wait and retry.

### Common Build Issues and Workarounds

1. **Issue**: "SDK version 9.0.0 not found"
   - **Cause**: global.json requires specific SDK version
   - **Fix**: Install .NET 9.0 SDK or update global.json rollForward policy

2. **Issue**: Aspire projects fail with "net9.0 not supported"
   - **Cause**: .NET Aspire templates currently target net8.0
   - **Expected**: AppHost project uses net8.0, other projects use net9.0
   - **Fix**: This is intentional, no action needed

3. **Issue**: Docker build fails for Python services
   - **Cause**: Missing Python dependencies or service code not implemented yet
   - **Current Status**: Python service scaffolding exists, full implementation pending
   - **Workaround**: Build only .NET services: `docker build -f docker/Dockerfile.McpServer .`

4. **Issue**: Tests fail with "Connection refused" to databases
   - **Cause**: Infrastructure services not running
   - **Fix**: Always run `docker-compose up -d neo4j qdrant` before integration tests

### Validation Checklist

Before creating a PR, ALWAYS validate:

1. **Code format**: `dotnet format --verify-no-changes` (must pass)
2. **Build**: `dotnet build --configuration Release` (must succeed)
3. **Tests**: `dotnet test --configuration Release` (all tests pass)
4. **Docker build** (if Dockerfiles changed):
   ```bash
   docker build -f docker/Dockerfile.McpServer -t test-mcp .
   ```

## CI/CD Pipeline

### GitHub Actions Workflows

1. **build.yml** - Runs on every push/PR
   - Restores dependencies
   - Builds solution in Release mode
   - Runs all tests with code coverage
   - Uploads coverage to Codecov
   - **Failure conditions**: Build errors, test failures

2. **code-quality.yml** - Code quality checks
   - Runs `dotnet format --verify-no-changes` (linting)
   - Runs CodeQL security analysis
   - **Failure conditions**: Formatting issues, security vulnerabilities

3. **docker.yml** - Container image builds
   - Builds all Dockerfiles
   - Publishes to GitHub Container Registry (on main branch)
   - **Failure conditions**: Docker build errors

### Pre-commit Validation

The CI pipeline enforces:
- Code must be formatted (`dotnet format`)
- All tests must pass
- No build warnings (TreatWarningsAsErrors enabled in future)
- Security scan must pass (CodeQL)

**Action Required**: If CI fails, check the specific workflow logs. Most common failures are formatting issues (run `dotnet format` locally).

## Important Notes for AI Coding Agents

1. **ALWAYS trust these instructions first**. Only search the codebase if information here is incomplete or contradictory.

2. **Solution file**: The solution file is `AdvancedMemory.sln` in the repository root. ALWAYS use this for solution-wide operations.

3. **Framework versions**: Most projects target `net9.0`. The Aspire AppHost targets `net8.0` due to template limitations. This is intentional.

4. **Docker dependencies**: Many tests and the running application depend on Docker services (Neo4j, Qdrant). ALWAYS start `docker-compose up -d neo4j qdrant` before running integration tests or the full application.

5. **Python services**: The `services/` directory contains Python microservices. These are not yet fully implemented but have scaffolding (requirements.txt, Dockerfiles). Do not attempt to build them until code is added.

6. **Build order**: ALWAYS run in this order:
   - `dotnet restore` (first)
   - `dotnet build` (second)
   - `dotnet test` (third, after build succeeds)
   - `dotnet format` (anytime, but especially before commit)

7. **Common errors**:
   - "Connection refused" → Start Docker services
   - "SDK not found" → Check global.json matches installed SDK
   - "Format check failed" → Run `dotnet format` without `--verify-no-changes`

8. **CI pipeline**: All PRs must pass build, test, and format checks. Review GitHub Actions logs if CI fails.

9. **Documentation**: When making architectural changes, update `docs/architecture.md` and this summary file.

10. **Secrets**: NEVER commit API keys. Use environment variables or .NET user secrets. Check `.gitignore` includes `.env`, `appsettings.Development.json`, etc.
